# Release Workflow

1. Run `pnpm bump patch|minor|major` from `main` — always pass the release level. `confirm: false` in `bump.config.ts` only skips the trailing "Bump?" confirmation; with no `release` pinned, a bare `pnpm bump` opens an interactive version prompt that hangs a non-TTY shell. The other behavior (commit message format, files to update, tag/push opt-out) is pinned in `bump.config.ts` — do not override it via CLI flags.
2. Push the resulting version commit to `origin/main` directly. This is the pre-approved `git push` exception in the root AGENTS.md "Ask first" list — do not ask again.
3. Wait for the CI run triggered by that push on `main` to go green before dispatching `Release`. The `Release` workflow runs no lint, type-check, test, or e2e — its only build is each package's `prepare` script firing during `pnpm install --frozen-lockfile` (a full package build, including the `exports` rewrite described in [project-structure.md](project-structure.md)) — so that CI run is the only gate between the version commit and npm, and a `prepare` failure on the release runner surfaces as an install failure.
4. Do **not** create or push tags locally. The `Release` GitHub Actions workflow (`workflow_dispatch`) reads the version from `packages/builder-rsbuild/package.json`, creates the tag, publishes to npm, and generates the GitHub release.
   - The tag is pushed **before** `pnpm -r publish` runs — an existing `vX.Y.Z` tag is not proof the packages published; verify on npm. Re-dispatching after a failed publish requires deleting the remote tag first (checkout uses `fetch-depth: 0`, so the stale tag makes the `git tag` step fail with "already exists").
   - `pnpm -r publish` publishes every non-private workspace member, and the workspace globs `sandboxes/**`, `scripts/**`, and `website` — any new workspace member outside `packages/` must set `"private": true`. Nothing in CI checks this.
