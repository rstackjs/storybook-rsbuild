# Dependencies

- After editing any dependency manifest (`package.json`, `pnpm-workspace.yaml`, `.npmrc`), run `pnpm install` immediately.
- After a `rebase`, `merge`, or `stash pop` that changed dependency files (including `pnpm-lock.yaml`), run `pnpm install` before any validation command (`build`, `test`, `e2e`, `check`) — stale `node_modules` produces failures that look like regressions.
- Commit the resulting `pnpm-lock.yaml` changes in the same branch. Never push dependency manifest changes without the matching `pnpm-lock.yaml` update.
- `storybook-rsbuild-scripts` is intentionally a root-only `devDependency`: package-local `rstack.config.ts` files resolve it from the root `node_modules` when registering their Rslib config with `define.lib()`, keeping this private workspace package out of published package manifests.
- In `packages/*`, dependency type is a bundle-vs-external switch, not dev-vs-prod: `createRslibConfig` enables `output.autoExternal`, which externalizes `dependencies`, `optionalDependencies`, and `peerDependencies` while leaving `devDependencies` bundled; each package's self-reference is an explicit external. Some runtime imports (e.g. `slash`, `pretty-hrtime` in `storybook-builder-rsbuild`) sit in `devDependencies` deliberately so they get vendored into the bundle — "fixing" them into `dependencies` changes what is published. Check the factory's external policy before reclassifying a dependency.
- `peerDependencies` are hand-maintained: Renovate's global rule disables `peerDependencies` updates, except the `storybook` group in `.github/renovate.json5`, which bumps `dependencies`, `devDependencies`, and `peerDependencies` for `storybook` / `@storybook/**` together in one PR. The `typescript` peer follows upstream per framework and is identical in every package (`^5.9.0 || ^6.0.0 || ^7.0.0` as of Storybook 11), so `check-dependency-version` checks it like any other peer.
- Non-Storybook peer ranges (`@rsbuild/core`, `react`, `react-dom`) are deliberately **wider** than the matching `devDependencies`. Never narrow them below the upstream renderer's supported range: Storybook 11's React renderer requires React 18+, so the React framework peers are `^18 || ^19` while their devDependencies pin 18.3.1. `pnpm check-dependency-version` only cross-checks that peer ranges agree between packages, so a narrowed range stays green while silently dropping supported consumers.
  - The deliberate exception is the v4 legacy-peer drop: v4 is the Rsbuild 2 / Rspack 2 line, so every package peers `@rsbuild/core ^2.0.0` and the builder carries no 1.x version branches. Related toolchain peers follow the same rule — their floor is the first release built on Rsbuild 2 (`@modern-js/app-tools ^3.0.0`, `@modern-js/plugin ^3.0.0`, `@rslib/core >= 0.22.0`), not an older major that would pull Rsbuild 1 in. Everywhere else the "wider than devDependencies" rule still holds, and framework peers stay aligned with upstream Storybook 11: `react ^18 || ^19`, `lit ^2 || ^3`, `vue ^3`, `react-native-web ^0.19.12 || ^0.20.0 || ^0.21.0`, `typescript ^5.9.0 || ^6.0.0 || ^7.0.0`.
- The `storybook` peer is the exception and is not free-form: `scripts/check-dependency-version.mts` asserts every `packages/*` package's `peerDependencies.storybook` is byte-equal to the installed `@storybook/<renderer>`'s own `storybook` peer (a guard against two copies of `storybook` in the pnpm virtual store). Align it exactly on every storybook bump — even when that narrows it — and run `pnpm check-dependency-version` after the edit.
- Before hand-bumping a dependency, check `.github/renovate.json5`: `allowedVersions` rules cap some versions on purpose and `ignoreDeps` lists packages updated only by hand. The `rstack` cap (a regex admitting only release/beta/rc versions, blocking canary tags) is explained only by its `groupName`. Treat an uncommented cap as deliberate — never lift one without asking.
